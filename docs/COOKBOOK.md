# 实战配方集（COOKBOOK）

配方不是口号：每个都给「成品长什么样 → 用哪些模板/模块 → 拼装顺序 → 关键注意点」，照着就能开工。拼装的通用规则（地基合并、前缀注册、冲突清单）在 [ASSEMBLY.md](ASSEMBLY.md)，配方里只写这个产品特有的部分。编号约定：`03` 指模板目录，`模块 06` 指 modules/ 里的文档。

---

## 配方 ① 付费课程频道

**成品**：用户买课 → 付费确认 → 进专属频道看课 + 在 Bot 里按课时顺序学、做测验解锁下一课；到期自动移出频道。支持人工确认和 Crypto Pay 两种收款。

**用料**：模板 **03**（强制订阅门禁）、**14**（付费会员）、**56**（课程/LMS）、**62**（加密支付）；模块 06（订阅校验）、13（支付发货）、49（Crypto Pay）。

**拼装顺序**
1. 以 56 为底：先跑通建课、加课时、测验解锁的裸流程（进度键 `learn:`）。
2. 接 14 的订单状态机：买课 = 下单 → 待确认 → 开通；开通动作同时写会员记录 `sub:`（到期时间）和课程进度里的 `paid` 标记。
3. 接 03 的门禁：判定源从「查 getChatMember」换成「查 `sub:` 是否在期」——判定外形（返回未满足清单）不变，换的是内里。课程频道同时是会员频道，CHANNEL_ID 只写一份。
4. 接 62 当第二条收款轨：发票 payload 透传订单号，Webhook 验签通过后调用与 `payok:` 同一个开通函数。两种收款共用一条发货路径。
5. 挂 Cron：14 的到期清扫（每天一次）+ 56 无定时需求，别多挂。

**关键注意点**
- 发货必须幂等：62 的 Webhook 会重投，靠 `paid:` 标记防重复开通（模块 49 的红线实现照抄）。
- 测验答错不写进度——这是 56 实测验证过的口径，别在缝合时「顺手」改掉。
- 先在测试 Bot 上走完 L3/L4（下单→确认→进频道→学课→到期清扫），再上真频道。

## 配方 ② 连锁小店

**成品**：你运营一个母体，店主交 Token 就克隆出自己的小店；总部维护货源池，店主一键上架加价卖，买家在子店下单、店主确认后自动弹卡密。

**用料**：模板 **32**（母体 Bot）、**33**（商城 Bot）；模块 21（多租户托管）、22（商店购物车）、23（商城连锁）。

**拼装顺序**
1. 先单独部署 32，跑通入驻向导：交 Token → getMe 验真 → AES-GCM 加密存 `bot:` → 代设 `/w/<slug>` Webhook。
2. 再部署 33 验证商城内核本身：总部货源 `mall:prod:`、子店上架、购物车、下单、payok 发货，全链先在单店形态跑通。
3. 合体：把 33 的商店内核注册为 32 的一种子 Bot 类型，租户数据全部走 `t:<botId>:` 前缀隔离；店主在母体里的管理命令与在子店里的店主命令分开注册（模块 02 分级菜单）。
4. 最后接熔断：母体管理员一键停用违规子店（33 的 /mstop 与 32 的租户停用是同一件事，别做两套）。

**关键注意点**
- **红线：不代收代付。** 钱直接进店主自己的收款通道，母体只管开通与发货逻辑；这一条写进店主协议和代码注释。
- 一个 Token 只能挂一个 Webhook：店主把 Bot 交给母体后，自己不要再去别处 setWebhook，会互相顶掉。
- Token 只存密文、列表只显掩码；给店主留 /revoke 兜底说明（模块 21 的安全清单逐条对）。

## 配方 ③ 社区全家桶

**成品**：一个群的全套运营：新人联邦黑名单拦截 + 违禁词过滤、每日签到积分、群内竞答赛季、活跃统计日报。

**用料**：模板 **04**（群管理）、**13**（签到抽奖）、**26**（竞答游戏）、**22**（群统计）、**48**（联邦群管）；模块 11、16、18、33。

**拼装顺序**
1. 以 04 为底（群消息入口最全），先跑通验证/欢迎/过滤。
2. 接 48 的联邦检查：进群事件先查 `fban:` 名单，命中直接处理并结束，不再往下走。
3. 接 22 的统计计数：在群消息分发的最前端计数（msgs/users），统计键按天分 + TTL 35 天。
4. 接 13、26 的命令与回调：`/qd`、`quiz:` 等前缀与 04 的命令零冲突，查模块 03 注册表确认后直接并入 handle()。
5. 命令表合并：群管理员命令留在 USER 表（它们给群管理员用，不是 Bot 白名单管理员），这点和私聊 Bot 的分级逻辑不同，别照搬。

**关键注意点**
- **群消息处理必须串行定序**：联邦检查 → 04 过滤 → 统计 → 游戏/签到。顺序错了会出现「广告被统计计入」「封禁用户还能签到」这类缝合 bug。
- 部署前去 BotFather `/setprivacy` Disable，否则 Bot 只收得到命令，过滤和统计全失效。
- allowed_updates 取并集，必须含 `chat_member`（进退群与联邦拦截都靠它）。

## 配方 ④ 内容订阅站

**成品**：抓 RSS 源自动发频道；付费墙频道只有会员能进；你自己的脚本/监控也能通过一个网址接口往频道推消息。

**用料**：模板 **11**（RSS 推送）、**20**（消息推送 API）、**14**（付费会员）；模块 15（RSS）、13（支付发货）。

**拼装顺序**
1. 先部署 11 跑通抓取：第一次运行只播种不推送（`rss_state` 落盘），确认去重正常后再让它正式推。
2. 接 14：把 11 的推送目标拆成两个频道——免费频道全量推，会员频道推付费内容；会员开通/到期逻辑完全复用 14，不改判定。
3. 接 20：给 Worker 加 `/push?key=` 路由，你的爬虫、服务器监控、自动化脚本都能往频道发消息；key 用独立变量，和 WEBHOOK_SECRET 分开。
4. Cron 错峰：11 的抓取（如每 30 分钟）与 14 的到期清扫（每天一次）不要挤在同一分钟触发。

**关键注意点**
- 11 的 KEYWORDS 过滤在 CONFIG 里配，源多了先过滤再推，别把频道变垃圾场。
- /push 接口的 key 泄露 = 任何人能往你频道发消息：key 只放服务器脚本里，怀疑泄露立刻换。
- RSS 源在服务端被封是常见现象（实测有多个源抓不到）：抓不到就换源或降级为手动推，不要在代码里硬重试耗子请求额度。

## 配方 ⑤ 客服中心

**成品**：四层客服：用户私聊留言直达（轻量）→ 带编号工单协作（正规）→ 论坛话题里一单一话题（团队）→ Business 账号营业时间自动答疑（官方通道）。

**用料**：模板 **30**（客服工单）、**45**（论坛话题工单）、**53**（Business 代答）、**02**（双向客服）；模块 07（转发路由）、39（论坛话题）、10（审核流）。

**拼装顺序**
1. 先上 02：当天就能用的最低配——用户留言转发给你，你回复转发即回达。
2. 升 30：需要编号、状态、多人协作时换工单形态（`ticket:` 键），用户入口不变（还是私聊发消息），无感升级。
3. 升 45：客服团队多人时，把工单卡换成论坛话题：一单一话题，客服在话题里回复即回达用户；需要一个开了 Topics 的超级群 + Bot 有管理话题权限。
4. 加 53：有 Telegram Business 账号时接官方代答：营业时间关键词答疑、营业外留言转人工——转人工的落点就是前三层的工单入口。

**关键注意点**
- 四层是**同源演进**（都是转发+回复映射），不要四个一起部署抢同一个 Bot 的私聊入口；按阶段只启一层，映射键查模块 04 注册表防撞（`tmap:`、`topic:` 等）。
- 工单按设计是「工单卡先发到客服会话成功才落盘」：客服群 ID 配错会表现为用户侧提示失败，先用 08 查准 ID。
- 53 的前提是真 Business 账号在设置里连接授权，没有这个账号就停在 45，别对着 53 的代码干瞪眼。

## 配方 ⑥ 活动运营套装

**成品**：一场完整活动：邀请拉新统计 → 接龙报名 → 投票互动热场 → 订阅条件抽奖开奖公示。

**用料**：模板 **61**（活动抽奖）、**24**（接龙报名）、**19**（投票问卷）、**16**（邀请引流统计）；模块 14（邀请归因）、06（订阅校验）。

**拼装顺序**
1. 先部署 16 铺归因底座：深链 `ref_<uid>` + 专属进群链接双通道，活动开始前就要跑，否则早期拉新数据补不回来。
2. 接 24 做报名/占位（活动名额、候补名单），接 19 做活动中的投票互动（可改票、可匿名）。
3. 最后接 61 开奖：参与条件选「订阅频道」，点参与按钮时现场用模块 06 的 missingSubs 核验；开奖走 crypto 随机，名单存 `gw:`。
4. 时间双保险：开奖同时配 Cron 到点自动开和管理员 `/drawgw` 手动开——Cron 无法用 HTTP 触发测试，手动口是同一条代码路径，放心用它验收。

**关键注意点**
- 归因口径先说清：只统计「谁邀请了谁」，不做群发私信、不采集成员名单——这是本库的合规线（SURVEY 排除清单）。
- 61 的订阅核验通过路径需要 Bot 是目标频道管理员且参与者真订阅了，测试时用真频道验，别拿模拟数据下结论。
- 投票（19 自研）与原生 Poll（46）二选一：要数据落自己 KV、可改票，用 19；要官方原生体验，用 46，别混。

## 配方 ⑦ 个人助理套装

**成品**：一个私聊 Bot 包办个人事务：自然语言提醒、随手记账、闪卡复习、快递追踪、域名到期监控。

**用料**：模板 **36**（个人提醒）、**25**（记账）、**58**（闪卡记忆）、**67**（包裹追踪）、**81**（域名监控）；模块 34、47、48。

**拼装顺序**
1. 以 36 为底：它的时间解析（N分钟后/明天 9:30/每天/每周X）和 Cron 扫描是全套的时间中枢。
2. 接 25：记账是纯命令+文本触发（「记账 -25 午餐」），与 36 的提醒文本触发要分流——先判记账格式，再判提醒，别让「明天交房租 200」被两边抢。
3. 接 58：卡片键 `card:`、评分回调 `fc:` 独立，直接并入；复习到期提醒并进 36 的 Cron 扫描，不新开 Cron。
4. 接 67、81：都是「订阅 + Cron 轮询 + 变化才推」的监控形态，共用一个 scheduled 入口按前缀分发（`parcel:` / `dom:`）。

**关键注意点**
- 全部是个人数据：KV 键一律 `<前缀>:<uid>:...` 分区，这个 Bot 只给自己用就别做多用户权限了，但键分区习惯别省——以后拆开时不用改数据。
- 轮询类吃子请求：67/81 的 Cron 频率按「订阅数 × 频率」估算，个人量级无压力，但别把 81 的检查设成每分钟。
- 81 的证书监控需要外部探针（Workers 读不到对端证书），没配探针时只有 RDAP 域名到期——界面会如实标注「证书未监控」，别以为配了就全包。

## 配方 ⑧ 运维监控套装

**成品**：你的服务和资产有动静就推到你私聊：代码仓库事件、服务器存活、域名/证书到期、关注的直播开播。

**用料**：模板 **39**（GitHub 通知）、**81**（域名/SSL 监控）、**66**（直播提醒）；模块 **41**（通知适配器：webhook 验签 + dead man's switch 存活监控）。

**拼装顺序**
1. 先部署 39：每聊天独立密钥 + `/github/<聊天ID>` 地址，HMAC 验签后格式化推送——这是全套的「事件入口」样板。
2. 接模块 41 的存活监控：被监控服务定时来打卡（`ping:` 键），Cron 扫描超时未打卡的告警一次、恢复再通知一次。
3. 接 81：域名订阅走 RDAP 免 key 真查，证书走探针（见配方 ⑦ 的注意点）。
4. 接 66：YouTube 走频道页/RSS 免 key 真跑，Twitch 需 Helix 凭据；状态存 `live:`，只在开播/下播翻转时推。

**关键注意点**
- 监控类的核心是**防重复报**：每个监控对象都要有状态键记录「上次状态/已提醒等级」，81 的 30/7/1 分级 stage、41 的「告警一次」都是这个套路，缝合时别把状态键合并掉。
- Webhook 类入口（39）必须验签 + 用原始请求体验签，解析过的 body 再签会对不上（模块 41/49 都强调过这条红线）。
- 监控 Bot 自己挂了没人知道：给这套单独留一个最土的外部告警（比如另一个 Bot 的 /push 心跳），别让哨兵无声消失。

## 配方 ⑨ 游戏娱乐套装

**成品**：群里的游戏角：狼人杀开局、竞答赛季榜、HTML5 小游戏卡片分数榜。

**用料**：模板 **41**（狼人杀）、**26**（竞答游戏）、**51**（游戏平台）；模块 35、18、45。

**拼装顺序**
1. 先部署 26：单会话抢答最简单，题库在 CONFIG，赛季键 `quizpts:`。
2. 接 51：Worker 同时托管游戏页（贪吃蛇/2048），sendGame 发卡 → 回调按人签 HMAC 令牌拼 URL → 页面回 POST 分数 → setGameScore + `gscore:` 总榜。
3. 最后接 41：状态机最复杂，放最后单独验：报名 → 发牌 → 夜晚行动 → 天亮结算 → 公投 → 胜负。

**关键注意点**
- **41 的状态必须按人拆键**（`wolfp:`/`wolfn:`/`wolfv:` 一人一键）：整局单 JSON 在多人连点时会被 KV 最终一致覆盖丢数据——这是第三轮实测抓到并修掉的真 bug，模块 35 文首有修订说明，照修订版拼。
- 51 的游戏 short_name 必须先在 BotFather 注册且与代码逐字一致，否则 sendGame 直接失败（实测里就走过失败提示分支）。
- 游戏类全靠按钮回调：allowed_updates 必须含 callback_query；狼人杀身份牌靠私发，没私聊过 Bot 的玩家发不到牌会被自动剔除——开局前先让全员 /start 一次。

## 配方 ⑩ 跨境卖家套装

**成品**：面向海外买家的数字商品店：多语言菜单、卡密自动发货、加密币收款（免传统支付通道门槛）。

**用料**：模板 **15**（数字商品售货）、**62**（加密支付）；模块 **29**（i18n 多语言）、13（支付发货）、49（Crypto Pay）。

**拼装顺序**
1. 先部署 15 跑通单语言版：建商品、加库存、买家下单、管理员确认、弹卡密，全链 KV 读回验一遍。
2. 接 62 替换/补充收款步：创建发票时 payload 透传 15 的订单号 → Crypto Pay Webhook 验签（HMAC 密钥 = Token 的 SHA-256）→ 命中后调用 15 同一个 confirmAndDeliver 发货函数。人工确认保留为兜底通道，不删。
3. 套模块 29 的 i18n：文案从代码里抽成语言包，按用户 language_code 选包，命令菜单也按语言注册；商品名/描述这类数据型文本不走语言包，放 KV 里店主自填。
4. 时区与币种收尾：订单时间统一存 UTC 时间戳、展示时按买家时区换算；价格用稳定币计价避免汇率口径扯皮。

**关键注意点**
- 发货幂等是命门：Crypto Pay 的 Webhook 会重复投递，靠 `cppaid:`/`paid:` 标记保证一单只发一次货（62 实测验过重放只发一次）。
- 库存是数组弹一个少一个：并发下单时先占位再发货的顺序别改，改了就可能超卖。
- i18n 别 machine-translate 硬翻着上：先上英文 + 你最主要的客源语言两包，其余语言宁可回退英文，不要挂半成品。

## 配方之外的拼法

10 个配方覆盖的是常见成品形态。你的产品不在里面时：先按 [DECOMPOSE.md](DECOMPOSE.md) 把需求拆成动词，再去 [modules/README.md](../modules/README.md) 逐个动词挑积木，最后按 [ASSEMBLY.md](ASSEMBLY.md) 的五步缝合——本页所有配方都是这么来的。
