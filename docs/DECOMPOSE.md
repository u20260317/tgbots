# 如何拆解一个 Bot（拆解方法论）

> 看中任何一个现成的 Bot（自己的、开源的、甚至只是产品截图），用这五步把它拆成可复用的模块积木。本库的 42 篇模块文档全是这样拆出来的；新看到的好玩法，也按这个流程入库。

## 第一步：画交互面（它和世界打交道的全部入口）

先不看代码，把 Bot 的「面」列全：

| 维度 | 问什么 | 例子 |
|---|---|---|
| 更新类型 | 它收哪些 Update？ | message / callback_query / chat_join_request / inline_query / chat_member |
| 命令面 | 有哪些命令？谁能用？ | /start 所有人、/broadcast 仅管理员 |
| 按钮面 | 有哪些按钮？回调 data 怎么编码？ | `payok:<订单号>` |
| 外部面 | 它调哪些外部系统？ | 支付、RSS、行情 API、Cron 时钟 |
| 人的角色 | 哪几类人在用？ | 普通用户 / 管理员 / 群管理员 / 审核员 |

产出：一张交互面清单。拆解最常见的错误是只盯着命令，漏掉回调和定时任务——面没列全，拆出来的模块拼回去会缺胳膊少腿。

## 第二步：追状态（它的记忆存在哪、长什么样）

每个 Bot 都在「记事」，找到它全部的记忆：

1. **存哪**：内存（重启即丢）/ KV / 数据库 / 别的 Bot 的消息里（如转发坐标）。
2. **键怎么命名**：提炼成「前缀:ID」——这决定模块能不能共存（见 modules/04 的键注册表）。
3. **生命周期**：谁写、谁读、什么时候删/过期？有没有状态机（如订单 pending→paid→done）？

产出：状态清单 + 状态机图（有的话）。**状态即模块的边界**：两个功能共用一份状态，它们多半是同一个模块；状态完全独立的功能，可以放心拆开。

## 第三步：切动作（把业务流切成动词）

沿着用户旅程把流程切成动词短语：验订阅、发验证码、记账、审核、发货、开奖……每个动词问三个问题：

- 输入是什么（消息？回调？定时唤醒？）
- 读/写了第二步里的哪份状态？
- 输出是什么（发消息？改状态？调外部 API？）

产出：动作清单，每个动作标注它碰的状态。**只碰一份状态的动作是「纯模块」**，碰多份的要么再切细，要么它就是编排层（留在 Bot 本体里，不进模块库）。

## 第四步：定边界（什么进模块、什么留下）

按三个标准过一遍动作清单：

| 标准 | 进模块库 | 留在 Bot 本体 |
|---|---|---|
| 复用性 | 换个 Bot 还能用（验订阅、翻页、支付） | 只服务这个 Bot 的一次性逻辑 |
| 独立性 | 状态自闭环、对外只靠约定接口（env/参数） | 和本体状态深度耦合 |
| 稳定性 | 玩法成熟、接口不易变 | 还在快速试错 |

进库的模块必须补齐四件套：**【核心模块】横幅注释、KV 前缀登记、回调前缀登记、环境变量清单**——没有这四样，拼装时必撞车（见 ASSEMBLY.md 的冲突清单，全是没登记的代价）。

## 第五步：写成积木（模块文档的固定结构）

照 modules/ 里现有文档的格式写：

1. 一句话定位（这块积木干什么）
2. 原理（为什么这么设计，关键约束是什么）
3. 真实代码块（从能跑的模板里摘，不写伪代码）
4. 接入步骤（拼到别的 Bot 上要改哪几处）
5. 注意点（坑、边界、合规线）

## 一个完整的拆解示范：拆「商店 Bot」

| 步 | 结果 |
|---|---|
| 交互面 | 命令 /shop /cart /myorders；回调 cart:/shop:/pay；角色：买家/店主 |
| 状态 | 商品表、购物车 `cart:`、订单 `order:`、支付幂等 `paid:` |
| 动作 | 逛目录（读商品）、加购（写购物车）、结账（FSM 多步）、支付（外部）、发货（写订单+扣库存）、查订单 |
| 边界 | 目录+购物车进库（模块 22）；支付进库（模块 24 Stars / 13 人工确认）；结账向导归 FSM（模块 20）；店主订单后台是审核流变体（模块 10），不新拆 |
| 成果 | 一个商店 Bot = 22 + 20 + 24 + 10 四块积木 + 一份商品配置 |

## 拆解时的合规过滤

拆到「批量私信、采集成员、自动拉人、绕风控/DRM」这类动作时停手——它们不进库（完整排除清单见 SURVEY.md）。拆解是中立的工程动作，但入库是价值选择：积木会被反复拼装，坏积木的危害会被放大。
