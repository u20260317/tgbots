# 09 · 安全

## 本篇讲什么

Bot 的安全面：token 保管、webhook 验签、管理员鉴权、输入与注入、防刷防滥用，以及代管他人 token 时的加密与告知义务。这一篇不是「加分项」，是上线门槛。

## 核心概念

### 资产清单：什么最值钱

- **BOT_TOKEN**：Bot 的全部权限，等同密码 + 身份证。存放只进部署平台的 Secret；不进代码、不进 Git、不进聊天与截图；团队协作宁可各自用自己的测试 Bot，也不共享生产 token。泄露处置只有一个动作：BotFather `/revoke`，然后全环境换新。
- **WEBHOOK_SECRET / 各类业务密钥**（面板 key、推送 key）：同理按密钥管理，长度足够随机，按用途分开（一个泄露不连累其他）。
- **用户数据**：聊天内容、手机号、订单——按「最小化」原则，能不存就不存，存了要想清谁能看、存多久。

### 入口安全：谁能调动你的 Bot

- **Webhook 验签**：逐条校验 `x-telegram-bot-api-secret-token`（见 03 篇），不对直接 403。没有这一步，任何人都能伪造更新让你的 Bot 给任意人发消息、触发管理员逻辑。
- **管理员鉴权认数字 ID**：白名单比对 user id（模块 02 的 isAdmin）。绝不用用户名（可改、可冒充）、绝不用「群里身份」代替 Bot 管理员身份（两套名单，见模块 11）。
- **回调也要鉴权**：按钮谁都能点，管理员按钮（审核、发货、踢人）在回调里必须再验一次身份——「菜单里看不见」只是体验层，不是安全边界。
- **HTTP 接口**（面板、推送 API）：独立 key + 只给必要能力，key 走请求头或参数时注意别被日志明文记录。

### 输入处理：用户内容都是不可信的

- 拼 HTML/ Markdown 格式文本前转义用户内容，防格式注入与假链接（见 04 篇）。
- callback_data 是用户可篡改的（改客户端就能发任意 data）：解析要容错，参数里的 ID 不能直接当权限依据，关键动作回查状态。
- 文件与链接：用户发来的文件别无条件转发到公开频道（投稿类先审，模块 10）；URL 拉取类功能要防内网地址（SSRF 意识），别让 Bot 去访问你内网的服务。

### 防刷与滥用

- 按用户限流：命令频率、领奖/签到类一天一次的业务约束本身就是防刷，别只靠自觉。
- 验证码/订阅门禁挡机器人与小号（模板 04/03）；公开入口（投稿、目录提交）一律先进审核再公开。
- 经济系统（积分、邀请奖励）默认假设有人刷：归因去重、上限、异常人工复核（模块 14/16 的做法）。

### 代管他人 token：母体场景的特别义务

模块 21/23 的母体与商城要存别人的 token，标准再升一级：

- **加密存储**：AES-GCM 密文进 KV，解密密钥放 Worker Secret（模块 21 有已实测实现）；任何界面只显示掩码；日志、报错、统计里绝不出现 token 与敏感路径。
- **知情与退出**：入驻时明示代管意味着什么、数据怎么用、如何退出；用户随时可 BotFather /revoke 自行失效——这是用户的安全阀，要主动告知而不是藏着。
- **最小权限与审计**：母体管理员的敏感操作（停店、导出）留痕；一个 token 只挂一个 webhook 的冲突要在入驻时提示。

## 实操要点

1. 上线前自查清单：token 在 Secret 里？webhook 验签开着？管理员命令都验了 ID？回调验权？用户内容转义？四项缺一不上线。
2. 日志脱敏：打印更新用于调试时，把 token、手机号、密钥字段打码；调试完关掉详细日志。
3. 密钥轮换有预案：每个密钥都知道「在哪改、改完要重部署/重注册什么」。
4. 备份的是配置和数据，不是 token——token 丢了 revoke 重发即可，别为了「备份」把它明文存得到处都是。

## 常见坑

- **把「隐藏管理员命令」当安全**：手打命令照样到达。校验在服务端做（模块 02 反复强调）。
- **用一个万能 key 走所有接口**：面板、推送、回调共用一个密钥，泄露一次全军覆没。按用途分开。
- **调试时把完整更新打进公开日志/频道**：里面有用户隐私和可能的密钥。脱敏 + 私有渠道。
- **母体回显 token 让用户「确认」**：确认页只显示 Bot 用户名和掩码，原文永不回显。
