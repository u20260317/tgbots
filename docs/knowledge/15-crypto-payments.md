# 15 · 加密支付（Stars 之外）

## 本篇讲什么

06 篇讲了 Stars 与传统支付，这一 篇补上第三条线：加密支付。以 Crypto Pay（@CryptoBot 官方的支付服务）为样本讲发票与 Webhook 验签模型，再把 TON 生态支付的概念摆清，最后给出三条加密/平台路线与人工确认的选型对照。

## 核心概念

### Crypto Pay 是什么形态

Crypto Pay 是 @CryptoBot 提供的托管式加密支付 API：你在它的 @CryptoBot 里建一个应用、拿到 API Token，就能用 HTTP API 创建发票（指定币种如 USDT/BTC/TON、金额、有效期、自定义 payload），用户点开链接在 CryptoBot 里完成付款，支付结果通过 Webhook 推回你的服务。钱先进 Crypto Pay 的托管账户，提现规则、支持币种与费率以其官方文档为准。

与 Stars 的本质区别：**Stars 是 Telegram 平台内货币（Bot API 原生），Crypto Pay 是第三方服务商（独立 API + 独立账户体系）**，Bot API 本身并不知道这笔支付存在——发票链接就是一条普通 URL 按钮，付款状态全靠 Crypto Pay 的 Webhook 与查询接口。

### 发票与验签模型

1. **建票**：调 createInvoice，关键字段是 amount、asset（或法币计价 + 允许币种）、payload（放你的订单号，是对单锚点，和 06 篇的原则一致）。
2. **交付链接**：把返回的支付 URL 做成 url 按钮发给用户，话术里写清有效期。
3. **Webhook 验签（红线）**：回调头里带签名字段，其 HMAC 的密钥不是 Token 原文，而是 **Token 的 SHA-256 摘要**，签名对象是**原始请求体字节**。两个细节错一个就验不过：用解析后的 JSON 重新序列化去验签必挂（字节已变），拿 Token 原文当密钥也必挂。验签通过后再看事件类型（如 invoice_paid）与 payload 对单。
4. **幂等发货**：与 Stars 同理——发货只认支付成功事件，按发票 id / 订单号落幂等标记（如 `cppaid:`），Webhook 重试与「轮询补发货」双通道同时存在时更要靠幂等防双发。
5. **轮询兜底**：Webhook 可能丢（你的服务当时不可达），用 getInvoices 按状态定时对账，未发货的 paid 发票补发——Webhook 为主、轮询为底，是所有第三方支付接入的通用姿势。

### TON 生态支付（概念层）

TON 是 Telegram 深度绑定的公链，钱包侧有 @wallet 与 TON Connect 协议。Bot 场景里常见的不是「Bot 直接收款」，而是：Bot 发起支付意图 → 用户在钱包 App 里签名确认 → 链上转账 → 你的服务监听链上事件或查交易确认到账。这条路的特点是**非托管**（钱直接进你的钱包地址，没有服务商账户）、确认依赖链上状态、退款只能你主动再转一笔。它更适合已经身在 TON 生态的项目（NFT、DAO，见模板 74/75 的世界），接入与对账成本明显高于托管式 Crypto Pay。

有一条红线先说清：**任何要求代管用户私钥、代签交易的形态都不做**（第二轮盘点已把 DEX 代签名交易 Bot 列入排除清单）——模板只做「用户自己钱包签名」与「托管服务商发票」两类，不碰私钥。

### 四条收款路线选型对照

| 路线 | 托管方 | 到账确认 | 适合 | 主要成本/约束 |
|---|---|---|---|---|
| Stars（06 篇） | Telegram 平台 | successful_payment 事件 | 数字商品与服务（官方要求） | 平台抽成、兑换路径 |
| Crypto Pay | 第三方服务商 | Webhook + 轮询对账 | 加密原生用户、跨境小额 | 需服务商账户、费率以其官方为准 |
| TON 链上 | 无（用户钱包直付） | 链上交易确认 | TON 生态内项目 | 对账自建、无平台兜底 |
| 人工确认（模块 13） | 无 | 管理员肉眼 | 小额低频熟人 | 不可规模化、无自动对账 |

选型口诀：卖数字商品先 Stars（合规线）；用户群本来就用加密钱包、且商品形态允许，再评估 Crypto Pay；已在 TON 生态里玩资产，再考虑链上直付；什么都没想好、先跑起来，用人工确认过渡。

## 实操要点

1. 订单先落库再建票，payload 只放订单号，别把用户隐私塞进第三方系统的字段。
2. Webhook 端点要能吃「原始请求体」：在框架层先取 raw body 再验签，验完才 JSON 解析——顺序反了就永远验不过。
3. 发货与对账分离：Webhook 处理只做「验签 → 对单 → 幂等发货」，对账轮询放 Cron 慢跑，两边共用同一个幂等标记。
4. 金额与币种在发货前再查一次发票状态：不信任回调里自带的金额字段，以查询接口/验签后的事件为准，并与本地订单比对。

## 常见坑

- **验签密钥用错**：Crypto Pay 的 HMAC 密钥是 Token 的 SHA-256，不是 Token 本身——这是它家最著名的坑，文档里专门写了也要再踩一遍才长记性（本库模板 62 已按此实现并实测）。
- **拿回调金额直接发货**：回调可重放、可延迟；发货前对单 + 查状态 + 幂等，三件套缺一不可。
- **以为加密支付能绕开 Stars 政策**：数字商品在 Telegram 内的支付合规要求不因支付通道改变，政策口径以官方文档为准，别把通道选择当合规手段。
- **链上支付不做确认数管理**：看到交易就发货，遇到链重组/失败交易就资损。按金额大小设确认门槛，小额即时、大额等确认。
