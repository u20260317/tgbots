# 08 · 限流与性能

## 本篇讲什么

Telegram 平台的流量规矩（发多快会被拦）、429 怎么正确处理、广播怎么排队，以及 Cloudflare Workers 这一侧的资源上限。Bot 小的时候感觉不到，用户一多全是这一篇的问题。

## 核心概念

### 平台限额（量级，以官方 FAQ/文档为准）

- **全局**：大规模广播的经验上限约 30 条/秒量级，且这不是「可以一直顶格跑」的承诺。
- **单 chat**：私聊约 1 条/秒；同一群内约 20 条/分钟量级。给同一个人连发多条最容易先撞这里。
- **进群/动作类**同样有频控（改名、置顶、踢人等管理动作别循环猛调）。

具体数字会调整，动手前查官方 Bots FAQ；工程上的正确姿势不是背数字，而是**把发送做成可排队、可降速、可重试**的管线，数字变了只改参数。

### 429 与 retry_after

超限返回 429，响应里带 `parameters.retry_after`（秒）。正确处理：**严格按它等**，等完重试同一请求；连续 429 就指数退避并给队列降速。无视 retry_after 硬重试只会延长被限时间。其他错误别混进来重试：403（被拉黑/踢出）重试一万次也没用，应直接标记该目标失效；400 参数错要改代码不是重试。

### Workers 这一侧的上限

- **CPU 时间**：免费计划单次请求 CPU 时间很短（毫秒级，以 Cloudflare 文档为准），重活（大列表扫描、批量发送）要拆小、异步、用 Cron 分片续跑。
- **子请求数**：单次执行能发出的 fetch 次数有上限（免费版约 50，以 Cloudflare 文档为准）——本库的 DEAL 类抓取和广播模板都吃过这个亏，设计时先算账。
- **KV**：读便宜、写有每日额度（免费版约 1000 次/天量级，以官方为准），高频计数别一键一写，要聚合（模板 22 的按天聚合就是为此）。

### 广播的正确形态

给 N 个用户群发 = 一条队列慢慢发：按单 chat 间隔节流出队、429 全局降速、403 收集起来清理名单、进度落 KV 支持中断续跑。模板 09 的群发是小名单版；名单上万时按这个形态升级（模块 27 给了节流+重试的 tg() 增强版和分片思路）。

## 实操要点

1. 所有出站请求走统一封装（tg()），把节流、重试、错误分类做在一处，别散落在业务代码里。
2. 给每个 chat 维护最小发送间隔；群发任务启动前先估算总时长（条数 ÷ 速率），超限就分片到 Cron。
3. 可观测：记录每次 429 的发生点和 retry_after，限流参数靠数据调，不靠感觉。
4. 幂等与限流是一对：重试必须配幂等键（见 03 篇），否则退避重试会把发货、扣分执行两遍。

## 常见坑

- **循环里裸调 sendMessage 群发**：几百人就开始大面积 429，还拖慢 webhook 响应。入队慢发。
- **把 403 当网络问题重试**：用户拉黑 Bot 后每次广播都撞一次 403，既慢又脏名单——首次 403 就标记停用。
- **在 webhook 同步执行里做长任务**：超时 + 平台重试 + 重复处理三连。先回 200，重活异步（03 篇）。
- **KV 写爆额度**：每条群消息都写一次计数是典型死法，按天/按批聚合。
