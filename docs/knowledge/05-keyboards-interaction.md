# 05 · 键盘与交互

## 本篇讲什么

Bot 的「界面」只有两种键盘 + 命令菜单 + 深链这四样东西。这一篇讲清它们各自的定位、硬约束（回调 64 字节、深链参数规则、命令 scope），交互设计不出洋相全靠这里。

## 核心概念

### Reply Keyboard：客户端键盘

出现在输入框位置的自定义按钮阵列。它的本质是**快捷输入**：用户点一下，等于亲手发了一条按钮文字的消息。你的代码收到的就是普通文本消息，靠文字内容匹配来分发。特点：

- 一直驻留（直到被替换/移除），适合主菜单、高频入口。
- 能请求手机号/定位（专用按钮类型），这是 inline 键盘做不到的。
- 没有「回调」，也就没有转圈、没有回执问题；但也拿不到「点了哪条消息上的按钮」的上下文。

### Inline Keyboard：消息上的按钮

挂在某条消息下方（reply_markup），点一下产生 `callback_query` 更新（见 03 篇）。按钮四种：

- **callback 按钮**：带 `callback_data`，你的业务主力。
- **url 按钮**：直接开链接，无回调。
- **web_app 按钮**：打开 Mini App（见 07 篇）。
- **switch_inline 按钮**：把用户带去别的聊天框唤起本 Bot 的 Inline 模式（模块 26）。

硬约束：**callback_data 最长 64 字节**（UTF-8 字节数，不是字符数）。所以全库约定「前缀:参数」的编码（`cart:add:p1`），参数放不下就存 KV 用短 ID 映射——前缀注册表在模块 03 里，拼装时先查表防撞。

回调三件套（缺一出毛病）：按前缀分发业务 → `answerCallbackQuery` 回执（不回，按钮会转圈约几十秒，用户以为卡死）→ 需要刷新时 `editMessageText`/editMessageReplyMarkup 原地改，别新发消息刷屏。

### 深链：start 参数

链接 `t.me/<bot>?start=<参数>` 是 Bot 的「带参入口」：邀请归因（`ref_<uid>`）、文件领取（`f_<短码>`）、匿名信箱（`box_<uid>`）全靠它。约束：参数最长 64 字符、字符集限字母数字与 `-_`（以官方文档为准）；用户已启动过 Bot 时再点深链，需要靠 `startgroup`/重新触发等方式感知，别假设每次点击都有 /start 到达。群版是 `?startgroup=`。

### 命令菜单与 scope

`setMyCommands` 注册的命令列表决定用户点 `/` 时看到什么。scope（作用域）机制：默认列表对所有人生效，还可以给「全部私聊」「全部群聊」「指定 chat」「指定群管理员」分别注册不同列表——本库的分级菜单就是用「默认=用户命令 + scope=chat 给管理员注册全集」实现的（模块 02）。命令名只能小写字母、数字、下划线，最长 32（以官方为准）；描述会多语言展示，可按 language_code 分别注册（模块 29）。

## 实操要点

1. 主菜单用 reply keyboard、流程操作用 inline keyboard，两者别混用定位。
2. callback_data 设计先查模块 03 的前缀表；新前缀顺手登记，拼装时全靠它防撞车。
3. 按钮文字给用户看，callback_data 给代码看——改文字不用动逻辑，改 data 格式要想清楚旧消息上的老按钮怎么办（它们会带着旧格式点回来）。
4. 危险操作（删除、付款、踢人）按钮加二次确认：第一下换出「确认？」键盘，而不是直接执行。

## 常见坑

- **按钮点了转圈**：没回 answerCallbackQuery，或回调处理抛错没兜底。
- **callback_data 超长被拒**：把整段 JSON 塞进 data 是最常见死法，改存 KV 传 ID。
- **老消息上的按钮点了报错**：你升级代码改了 data 格式。分发时对未知/旧格式前缀要优雅回执「已过期」，别抛异常。
- **命令菜单改了不生效**：改完要重新调 setMyCommands（本库在 /setWebhook 时顺带注册），且客户端有缓存，稍等或重启客户端再看。
