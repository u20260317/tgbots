# 高频问题（FAQ）

按部署 / 运行 / 额度 / 安全 / 群相关 / 数据六组排，每问给可操作答案。部署期的现象速查也在 [DEPLOY.md](DEPLOY.md) 末尾有一张表；系统性排障看 [知识库 11 · 调试与运维](knowledge/11-debug-ops.md)。

## 部署

**Q：部署完 Bot 完全不回消息，先查哪三处？**
一查 Webhook：浏览器打开 `https://api.telegram.org/bot<你的Token>/getWebhookInfo`，看 url 是不是你的 Worker 地址、last_error_message 有没有报错。二查变量：BOT_TOKEN 是否填错、是否设成了 Secret 且值完整。三查部署：变量或代码改完后有没有重新点 Deploy——这是最高频的原因。完整版见 [DEPLOY.md](DEPLOY.md)。

**Q：打开 /setWebhook 返回 403 是什么问题？**
网址里的 `key=` 和 Worker 变量 `WEBHOOK_SECRET` 对不上（或压根没设这个变量）。/setWebhook 是内置路由，口令不对一律 403，这是设计不是故障。

**Q：打开 Worker 地址显示「BOT_TOKEN 未配置」？**
变量没加，或加完没重新 Deploy。Cloudflare 控制台加变量后会提示需要重新部署，照做即可。

**Q：改了代码或变量为什么不生效？**
两个原因：①没点 Deploy；②刚部署完的传播期——实测中多次出现部署后首个请求 404/500、setWebhook 报 1042 错，等几十秒到几分钟重试即恢复（[TESTING.md](TESTING.md) 里有大量这类记录，均已注明非代码问题）。先等再查，别急着改代码。

**Q：一个 Bot 能同时部署到两个 Worker 吗？**
不能。一个 Bot 只能挂一个 Webhook，后 setWebhook 的会顶掉先前的。母体类模板（32/54）代管子 Bot 时同理：子 Bot 交给母体后不要再自己去挂别处。

## 运行

**Q：群里 Bot 只对命令有反应，普通消息像没看见？**
这是 Telegram 的群隐私模式（Group Privacy）：默认开着时 Bot 只能收到命令、回复和 @ 它的消息。去 BotFather 发 `/setprivacy`，给该 Bot 选 **Disable**。需要读群消息的功能（违禁词过滤、群统计、自动翻译等）都受这一条制约，详见 [DEPLOY.md](DEPLOY.md) 第 5 步。

**Q：往频道/群发消息失败，报 chat not found 或 not enough rights？**
先用 08-id-tools 查准 ID（群是 -100 开头的负数，别用错格式），再确认 Bot 是该频道/群的管理员且勾了对应权限（发帖/删消息/封禁按需）。

**Q：为什么 Bot 不能主动给某个用户发消息？**
平台规则：Bot 只能给点过 /start 的用户发私聊。没 start 过的用户，邀请链接、答题私信、身份牌都发不过去——12 答题模式、29 匿名信箱、41 狼人杀发牌都受这条限制，各模板 README 里有各自的兜底说明。

**Q：按钮点了转圈没反应，或提示 query is too old？**
回调必须回 answerCallbackQuery，转圈多半是处理函数抛错或没回这一步；query is too old 是回调查询过期（用户点了很久以前的按钮），属正常现象，忽略即可。回调机制看 [知识库 05](knowledge/05-keyboards-interaction.md)。

**Q：定时任务（Cron）为什么没按时发？**
先确认部署时加了 Cron Trigger 且表达式对；再确认代码里的到期判定用的是时间戳比较而不是「正好等于某分钟」（本库的省流设计是低频唤醒 + 时间戳判定，如 21 用 */5 扫）。Cron 路径无法用 HTTP 手动触发验证，只能等真实触发或用模板自带的手动口（如 /pushnow、/sweep）验收，见 [TESTING.md](TESTING.md) 的已知限制。

## 额度

**Q：Workers 免费额度够多少用户用？**
免费版每天 10 万次请求，每条消息/每次按钮算 1 次，个人和小社群绰绰有余。真正的约束是单次请求的子请求数与 CPU 上限：抓取/轮询类模板（11/60/66 等）都做了低频与去重设计，照默认节奏用没问题。量级估算方法看 [知识库 08](knowledge/08-limits-performance.md)。

**Q：KV 是什么？不绑 KV 能跑哪些模板？**
KV 是 Cloudflare 的键值存储，本库拿它存映射、名单、索引、账本这类小数据（文件本体存在 Telegram 那边）。不绑 KV 能跑的：01–05、07、08、20、27、28、40、59 等无状态模板；需要 KV 的完整清单在 [根 README 的安全须知](../README.md) 里，逐个模板的 KV 需求也标在目录表的最后一列。

**Q：KV 的数据为什么刚写完读不回来？**
KV 是最终一致：写入后在全球边缘传播需要时间，实测个别键读回延迟可达约 2 分钟。这不是 bug——[TESTING.md](TESTING.md) 里多次靠「等待 + 逐键直读」区分了真 bug 与传播延迟。自己写 Bot 时记住：刚写完立刻 list 扫描是最容易被延迟坑的读法，逐键直读更可靠；高并发写同一键还会互相覆盖，41 狼人杀因此改成了按人拆键（见模块 35 文首修订说明）。

## 安全

**Q：Token 泄露了怎么办？**
立刻去 BotFather 发 `/revoke` 选对应 Bot，旧 Token 当场作废；把新 Token 填回 Worker 的 Secret 变量并重新 Deploy。Webhook 不用重挂（地址没变）。

**Q：为什么管理员判定用数字 ID，不用用户名？**
用户名可以改、可以被冒充（同名不同号），数字 ID 不会变也不会重。所有模板的 ADMIN_ID 都填数字 ID，先用 08 查准。菜单隐藏只是体验层，真正的拦截靠业务里的 isAdmin 校验，两层缺一不可（模块 02）。

**Q：让母体 Bot 代管别人的 Token 安全吗？**
这是全库最敏感的形态，32/54 的口径是：Token 用 AES-GCM 加密后才存 KV、列表只显示掩码、绝不落日志、子 Bot 违规有熔断开关、用户随时可 /revoke 让托管的 Token 作废。建议只给自己或熟人用；机制与义务看模块 21 和 [知识库 09](knowledge/09-security.md)。

**Q：Webhook 为什么要带密钥校验？**
/webhook 地址是公开的，没校验的话任何人都能伪造更新打进来（假装管理员发命令）。本库双保险：setWebhook 时登记 secret_token，Worker 逐请求验请求头；/setWebhook 路由另有 key 口令。

## 群相关

**Q：群管理类 Bot 需要给哪些管理员权限？**
按功能勾：删消息（过滤/守卫）、封禁成员（ban/mute/联邦）、置顶（规则帖）、邀请链接（会员开通）。多给无益，少给就报 not enough rights。03 强制订阅有个特殊要求：Bot 必须是「被订阅频道」的管理员，否则查不到成员状态。

**Q：话题（Topics）群和普通群有什么不一样？**
话题群里每条消息带 message_thread_id，回复必须带上同一个 thread id 才能进对应话题。45 论坛工单就是靠这个做「一单一话题」；普通群里部署 45 不会报错，但话题组织能力用不上。机制看模块 39。

**Q：联邦封禁（48）和单群封禁（04）选哪个？**
只有一个群：04 就够。多群联盟、想共享黑名单：48——一个群封的人所有成员群都拦，配套 CAS 查询和群笔记。代价是需要各群管理员都把 Bot 拉进去并注册（/fedjoin）。

## 数据

**Q：我的数据都存在哪？会不会丢？**
状态在 Cloudflare KV（映射/名单/账本），文件本体在 Telegram（私有频道转存或 file_id 直存）。诚实说：KV 是运营级存储、不是备份级存储——它没有回收站，键被删或覆盖就没了。重要账本（如 15 的库存、25 的账本）建议定期导出留底；真到了需要强一致和关系查询的量级，该考虑 D1（见 [ROADMAP.md](ROADMAP.md) 的候选项）。

**Q：模拟测试和真人测试有什么区别？为什么记录里很多 L4 没有 L5？**
测试分五级（L1 语法 → L5 真人），定义在 [TESTING.md](TESTING.md)。模拟测试用构造的更新打 Worker：能验证处理逻辑和 KV 等副作用，但模拟 chat 在 Telegram 侧不存在，「发消息」这一步必然失败，所以判定不看消息送达、看状态落盘。L4 证明业务真的跑通，L5 证明真人体验无误——关键 Bot 上线前建议自己点一遍升 L5。

**Q：为什么全库坚持单文件？拼不到一起怎么办？**
单文件 = 零依赖、零构建、拖进 Worker 就跑，也是「积木可拆」的前提：所有模板共享同一副骨架（配置层/tg() 通信层/入口路由/业务分发），模块带横幅、回调与 KV 键带注册前缀，照 [ASSEMBLY.md](ASSEMBLY.md) 五步就能拼。代价是单个 Bot 的复杂度有上限——真到了多服务协作的量级，应该拆成多个 Bot 分工，而不是把一个文件堆到几千行（取舍见 [DESIGN.md](DESIGN.md) 与 [知识库 10](knowledge/10-architecture-scaling.md)）。
