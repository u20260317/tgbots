# 积木组装说明书：把多个 Bot 拼成一个

每个 `worker.js` 都按同一套规范写，所以模块可以拆出来拼装：

## 为什么能拆

1. **地基统一**：每个文件都是同四层——文件头配置说明、`tg()` 通信层、Worker 入口路由、`handle()` 业务主流程，函数签名和 env 变量读法完全一致，地基只需要一份。
2. **核心模块有标注**：代码里带 `` 横幅注释的就是可拆单元，横幅下面写了它干什么、靠什么数据。
3. **状态不打架**：无状态模块靠消息/按钮坐标工作；有状态模块的 KV 键天然分开（06 用 `f:` 前缀、09 用 `subs`、10 用 `index`），同一个 KV 就能共用。
4. **按钮回调带前缀**：`pub:`（发帖）、`cap:`（群验证）、`ok:/no:`（投稿审核）、`pg:`（菜单）、`lp:/get:/shr:/del:`（网盘）、`check`（强订验证）互不重名，拼在一起不会串线。

## 组装五步

1. **选模块**：从各文件里把带 `` 横幅的段落整段拷出来。
2. **合并地基**：`tg()`、入口路由只保留一份；入口里 `allowed_updates` 取并集（如 `["message","callback_query"]`）。
3. **合并变量**：各模块的 env 变量取并集，填到同一个 Worker 里（同名变量如 `ADMIN_ID`、`CHANNEL_ID` 本来就是同一个值）。
4. **合并 handle() 分发**：这是唯一需要动脑的一步，按顺序分流——先按聊天类型（私聊/群/频道），再按命令，再按回调前缀，把每类更新交给对应模块的处理段。
5. **改名去重**：同名辅助函数只留一份或改名（见下面冲突清单），然后整文件过一遍语法检查再部署。

## 已知冲突清单（拼之前先看）

| 冲突 | 涉及 | 解法 |
|------|------|------|
| `fileOf()` 同名但返回值不同 | 06（返回 file_id）/ 10（返回名称+大小） | 改名 `storeFileOf` / `driveFileOf`，或按调用处区分 |
| `/start` 每个模块都有自己的欢迎语 | 全部 | 做一个统一欢迎菜单：按钮分流到各模块（如「📮 投稿」「💬 联系管理员」「☁️ 我的网盘」） |
| 私聊普通消息的默认处理互相抢 | 01 管理员草稿 / 02 用户留言 / 05 投稿 / 10 存文件 | 按角色+意图分流：管理员→发帖草稿；普通用户先选模式（投稿/留言），文件类消息→网盘 |
| 群消息处理互相抢 | 03 守卫删帖 / 04 过滤删帖 | 串行执行：先过 03 订阅检查（不过直接删并结束），再过 04 的违禁词/链接过滤 |
| 变量名同义不同名 | 01 的 `CHANNEL_ID` / 05 的 `TARGET_CHANNEL` / 10 的 `STORAGE_CHANNEL_ID` | 不是冲突，是三个不同频道就填三个值；是同一个频道就填同一个值 |

## 现成组合推荐

- **频道运营全家桶** = 01 发帖面板 + 05 投稿审核 + 02 双向：管理员私聊=发稿，用户私聊先弹菜单选「投稿」还是「联系管理员」。
- **社群守卫** = 03 强制订阅 + 04 群管理：进群先验证+查订阅，再谈违禁词和广告过滤。
- **资源分发** = 03 强制订阅 + 10 网盘（或 06 文件分享）：取件前先过订阅校验，没订频道领不到文件，涨粉和分发一次搞定。

> 不想自己拼也行：告诉我想拼哪几个，我按上面规范拼成一个新的 `combo-*` 目录（依然单文件 worker.js），语法检查+推送 GitHub 后你直接部署。


## 组装实战：从零拼一个「付费课程频道 Bot」

需求：用户付费后进专属频道看课程帖。拆开看 = 强订门禁（没付费进不去）+ 会员支付（买→开通→到期踢）+ 频道发帖（往频道里发课程）。正好是 03 + 14 + 01 三块积木，全在库里。

**第 1 步：选积木、查注册表**
- 门禁：03 的 `missingSubs` + `joinKeyboard`（模块 06），回调前缀 `check`。
- 支付：14 的订单状态机 + grantMembership（模块 13），回调 `payok:`/`payno:`，KV 键 `order:`/`sub:`。
- 发帖：01 的 publish（模块 05），无回调冲突。
- 查 modules/03 前缀表、modules/04 键注册表：三者前缀/键零冲突，可直接拼。

**第 2 步：定地基**
用任意一个模板的 worker.js 当底（建议拿 14 的，它的 KV 读写工具最全），保留：tg()/send、webhook 入口与验签、模块 02 的分级菜单（命令表最后统一填）。

**第 3 步：逐块接入（顺序：先状态、后动作）**
1. 先把 14 的 `getKV/putKV` 与订单/会员读写搬进来，跑通 /plans → 下单 → 管理员 payok → 发邀请链接的裸流程（此时还没有门禁）。
2. 再接 03 的门禁：把「必订频道」换成「会员频道」，判定逻辑改为查 `sub:<uid>` 是否在期——注意这里**改的是判定源不是判定形**：missingSubs 的外形（返回未满足清单）保留，内里从 getChatMember 换成查会员状态。这就是积木接口稳定的价值。
3. 最后接 01 的发帖：管理员私聊发稿 → copyMessage 到会员频道。发帖目标和门禁频道是同一个 CHANNEL_ID，在 CONFIG 里只写一份。

**第 4 步：缝合三件套**
- /start 按用户状态分流：没买过→看套餐；在期→显示到期时间；过期→续费入口。一个入口、三条分支，靠状态判定，不要堆三个命令。
- 命令表：USER 放 start/plans/my，ADMIN 放 subs/sweep/post（照模块 02 分级）。
- Cron 挂 14 的到期清扫（每天一次），和发帖无关，别忘了在部署时加 Trigger。

**第 5 步：按 TESTING.md 的分级自测**
L1 语法 → L2 部署+webhook → L3 模拟更新走完「下单→确认→进频道→发帖」→ L4 读回 KV 验证 order/sub 状态 → L5 真人全流程。拼装 Bot 的 bug 大多出在缝合处（状态判定源、ID 写错），L3/L4 别省。

拼完回头看：三块积木一行没改接口，改的全是 CONFIG 和缝合分支——这就是「像搭积木」的实际含义。
